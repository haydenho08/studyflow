# Deploying StudyFlow (Render + Neon)

One Docker container on **Render** serves both the API and the built React app. The database is **Neon** (hosted Postgres). Both have free tiers; check their current pricing pages, since terms change.

```
browser ──HTTPS──▶ Render web service (Docker: FastAPI + static React build) ──TLS──▶ Neon Postgres
```

## 1. Neon: the database

1. Sign up at **neon.tech** (signing in with GitHub is fine).
2. Create a project: name `studyflow`, the latest Postgres version, and a **region close to where you'll run Render** (e.g. AWS US East (Ohio) with Render's Ohio region). Every query crosses between the two, so distance is latency.
3. On the project dashboard, open **Connect**, and copy the connection string. It looks like:
   `postgresql://<user>:<password>@<endpoint>.<region>.aws.neon.tech/neondb?sslmode=require`
   Either the pooled or the direct string works (the app doesn't depend on session settings). For one small service, the **direct** one (pooling switched off) is the simplest.
4. Treat that string as a password: don't commit it, and don't paste it into chats or issues.

## 2. Render: the app

1. Sign up at **render.com** with GitHub. When it asks which repositories it may access, choose **only `haydenho08/studyflow`** (least privilege).
2. **New → Blueprint** → pick `studyflow`. Render reads [`render.yaml`](../render.yaml) and proposes one free web service built from the [`Dockerfile`](../Dockerfile).
3. It asks for **`DATABASE_URL`**: paste the Neon string. `JWT_SECRET_KEY` is generated by Render automatically. **Apply**.
4. The first build takes a few minutes. On start-up the container runs `alembic upgrade head` (creating the tables in Neon), then starts uvicorn on Render's `$PORT`.
5. Open the URL Render shows (`https://studyflow-….onrender.com`) and check `/api/health` → `{"status":"ok"}`, then register an account.

From then on, every push to `main` deploys **only after CI passes** (`autoDeployTrigger: checksPass`).

## 3. The demo account (automatic)

`render.yaml` sets `DEMO_ENABLED=true`, which turns on the login page's **Explore the demo** button (`POST /api/auth/demo`). Nothing to seed by hand:
- The first click creates `demo@studyflow.app` with sample data.
- Any click when the data is **over an hour old** rebuilds it around *today*, in the visitor's time zone. The demo never shows a stale week, and anything an earlier visitor typed in is cleared out.
- Each rebuild gives the account a new random password, so the button is the only way in.

To reset it by hand anyway (e.g. right before an interview), run this from the repo root. It asks for the Neon connection string at a hidden prompt and keeps it only for that one command:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File backend\scripts\seed_demo_remote.ps1
```

(That sets the demo's password to `studyflow-demo` until the next automatic rebuild.)

## 4. Email (optional: password reset, changing email)

Out of the box `MAIL_BACKEND` is unset, so it's `none`: the app hides **Forgot password?** and the change-email form, and everything else works. To switch them on, use any SMTP provider. [Resend](https://resend.com) has a free tier; you need to verify a domain you own to send from it.

In Render → the service → **Environment**, add:

| Key | Value |
|---|---|
| `MAIL_BACKEND` | `smtp` |
| `SMTP_HOST` / `SMTP_PORT` | from the provider (Resend: `smtp.resend.com`, `587`) |
| `SMTP_USERNAME` / `SMTP_PASSWORD` | from the provider (Resend: `resend` and an API key); mark the password **secret** |
| `MAIL_FROM` | `StudyFlow <no-reply@your-verified-domain>` |
| `PUBLIC_URL` | `https://studyflow-q3u0.onrender.com` (the address used in emailed links) |

Save, and Render redeploys. `GET /api/config` then says `"email_enabled": true`, and the links appear. If sending fails, the app logs the error and carries on; the person sees the same "we've sent a link" message either way.

## 5. Rate limits (automatic)

Login lockout and the other limits (see [Stage 12](stage-12.md)) are on by default (`RATE_LIMIT_ENABLED=true`), and the counters are stored in the database, so a redeploy doesn't reset them. Nothing to configure. To let someone back in early, wait out the window (15 minutes for logins), or delete their counter in Neon's SQL editor. Keys are hashed, so hash the same way:

```sql
DELETE FROM rate_limit_counters
WHERE key = encode(sha256(convert_to('login-account:' || lower('alice@example.com'), 'UTF8')), 'hex');
```

## Free-tier behaviour to expect

- Render's free web services **sleep when idle**; the first request afterwards takes a while (cold start). Mention it next to the link ("may take ~30 s to wake up").
- Neon's free compute also scales to zero when idle and wakes on the first query.
- Migrations run at container start. That's fine for one instance; with several instances you'd run them once as a separate release step.
